# NTPU AI 登入測試

> build 23 已依使用者要求移除 App 的登入診斷按鈕與報告介面。下列診斷流程保留為歷史紀錄；新版請使用文末「使用手機保存的學校帳號」步驟。

目標是確認 iPhone WKWebView 上校方 SSO 的實際登入流程，以評估能否在經核對的官方表單中使用手機 Keychain 已保存的帳密。診斷模式只觀察網頁結構，不代填帳密；build 23 起另提供由使用者點選的本機帳號登入功能。三個服務帳密相同，不代表它們的 Cookie、Session 或驗證方式相同。

1. 更新到包含此功能的 TestFlight build 20。在「我的 → 學校帳號與同步」確認本機學校連結正常；不要展示或提供密碼。
2. 開啟懸浮 AI，點標題列的「AI 資料設定」圖示，選「開始登入診斷」。
3. 在可見的 NTPU AI 官方網頁按「使用學校帳號登入」。在校方頁面自行輸入帳密並完成任何驗證。不要複製頁面原始碼或開發者網路紀錄。
4. 登入成功或遇到阻擋後，按標題列「完成」，或用同一個選單進入「查看登入診斷」。
5. 按「複製」，只回覆這份 JSON 報告。報告只有官方主機、經遮蔽的路徑形狀、HTTP 狀態、欄位數、SAML／驗證碼／一次性驗證提示及是否已登入；不包含帳密、欄位值、Cookie、URL 查詢參數或原始頁面。外部主機只標示為 `[external]`。
6. 按「結束診斷」停止觀察。如果一開始就已登入，這次只驗證了 Session 保留；若想測首次登入，可以自行在官方頁登出後再操作，App 不會自動登出或清除你的網站資料。

## 結果如何用於下一步

- 有唯一的官方帳號／密碼表單且不要求額外驗證：可以再核對確切表單與目的地，實作由使用者按一次「使用本機學校帳號」後填入；尚不能只憑欄位數就開始傳送。
- 已有 Session 就直接登入：優先保留工作階段，避免重複登入；Session 過期仍需正常驗證。
- CAPTCHA／OTP／多因素驗證：仍須使用者在可見頁面完成，不能繞過。
- 外部登入、403 或其他失敗：需要確認校方允許的登入方式；不猜測 API、不盲目重試密碼。

診斷只涵蓋主框架中的校方頁面。若登入表單位於跨站 iframe，報告可能沒有表單結構，不能因此推論沒有驗證。此時只需另外描述是校方頁、Microsoft、Google 或其他登入服務，無須貼完整轉址網址。

## build 23：使用手機保存的學校帳號

已根據使用者提供的去值診斷與公開官方頁面核對路徑：AI `/auth/saml/login` → `saml2.ntpu.edu.tw/module.php/ntpuauth/login` 的原始 POST 表單 → AI `/auth/saml/acs` → AI 首頁。

1. 在「我的 → 學校帳號與同步」保存目前有效的帳密。
2. 若 AI 已登入，不需要重登；測試首次登入時可自行在官方頁登出。
3. 回到 AI 聊天，等待登入狀態檢查結束，點「使用已儲存的學校帳號登入」。等待過程有轉動提示，無須再輸入帳密。
4. 成功時應顯示「已連線」並可傳送訊息。若遇到額外驗證、帳密錯誤、表單變更或逾時，轉到可見校方頁面，使用者自行完成；不重試密碼。
5. 只回報是否成功、錯誤提示及 TestFlight build，不提供帳密、Cookie、SAML 或頁面原始碼。

帳密只在按鈕觸發且表單核對成功後從目前帳號的 Keychain 取得，透過 WebKit 參數填入校方原始表單，不寫入腳本原始碼或報告、不送到聊天模型。舊操作的非同步結果在取消或開始新操作後失效；關閉面板取消尚未完成的流程。這個功能的合成測試及編譯不等同於真實手機 SSO 已成功。登入診斷期間不啟用代填。
